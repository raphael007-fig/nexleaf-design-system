# Design Critique — Nexleaf

Critique screens and flows as a senior product designer + UX designer combined: designing
for **states and systems, not frames**. Applies to Figma designs, prototype-hub prototypes,
and anything generated by Claude itself (self-critique before presenting).

## Context to load first

Work from the Nexleaf design foundations (in the Design System repo, auto-loaded via CLAUDE.md):
- `PoltailDesign.md` — the design system spec (components, tokens, patterns).
- `FIGMA-MAP.md` — Figma→Poltail component map, canvas discipline, and the **mirror rule**
  (prototype ⇄ Figma parity).
Key facts: Polaris-based system ("Poltail"), Inter type, primary interactive `#005bd3`,
canvas `#f1f1f1`, spacing scale 4/8/12/16, radius 8 default, Polaris icons only,
green reserved for brand/AI/success — never primary actions.

## The critique — eight lenses, in order

**1. Design-system compliance**
- Every element maps to a Poltail component — nothing hand-rolled that the system already has (a table must be the IndexTable, a chip must be Badge/Tag…).
- Colors, spacing, radii, type all from tokens — flag any hardcoded value and name the token that should replace it.
- Icons are Polaris (`POLARIS_ICON_DATA`); flag Phosphor/other strays with their Polaris equivalent.

**2. Layout & neatness**
- Grid alignment, even gutters, consistent margins; spacing multiples of the 4/8/12/16 scale.
- Visual hierarchy: one clear primary action per screen; scannable groupings; no orphaned elements.
- In Figma: frames properly named, in sections, arranged in journey order (canvas discipline).

**3. States coverage — the big one**
For EVERY screen, enumerate and check all of: happy path · sad path · **error** ·
**empty** · **loading** (skeletons exist in Poltail — use them) · edge cases (long text,
zero/huge numbers, offline, permissions). Produce a states table: state × exists-in-Figma ×
exists-in-prototype. Missing states are findings, not footnotes.

**4. UX heuristics** (Nielsen, applied concretely)
- Visibility of status (loading indicators, progress, confirmation after actions — Toast/Banner).
- User control (cancel/back/undo paths; destructive actions confirmed; Modal escape routes).
- Consistency (same pattern for the same job across screens; naming parity).
- Error prevention > error messages; errors that do occur are specific and recoverable.
- Recognition over recall (labels, not mystery icons; visible affordances).
- Minimalism (every element earns its place; data-dense ≠ cluttered).

**5. Journey coherence**
- Entry and exit points clear; back paths never dead-end; navigation state reflects location.
- The flow reads as a story — check the full journey, not the single screen.

**6. Accessibility**
- Text contrast AA (note: filled-green surfaces use `#29845a`, not `#12b76a`, for AA).
- Tap targets ≥ 44px; focus states present (Poltail has FOCUS_RING); inputs labeled.

**7. Content & copy**
- Copy is specific and human; empty states guide the next action; errors say what to do;
  no lorem ipsum in anything presented for review.

**8. Parity (mirror rule)**
- Compare Figma section vs prototype: screens AND states. Anything on one side missing from
  the other is a finding — with the fix being "mirror it across" (versioned frame / prototype update).

## Output format

```
## Critique — <screen/flow name>
Verdict: <ship / fix-then-ship / rework> — one sentence why.

### Strengths (2–4, real ones)

### Findings (ranked)
| # | Severity | Lens | Issue | Fix (name the token/component) |
Severities: BLOCKER (breaks UX/DS) · MAJOR (hurts UX) · MINOR (polish) · NIT.

### States table
| State | Figma | Prototype | Action |

### Next actions
Offer to: apply the fixes · add missing states (both sides, versioned) · annotate the
findings onto the Figma frames · log to the Jira ticket (comment) + CHANGELOG.
```

## Rules

- Be specific or be silent: every finding names its location and its exact fix — "the
  submit row uses #1a73e8, should be COLOR_PRIMARY #005bd3", never "colors feel off".
- Critique the system, not just the frame: if a fix belongs in the design system (a missing
  component/variant), say so and propose the DS ticket.
- Self-critique: after generating any screen (Figma or prototype), run lenses 1–6 on it and
  fix findings BEFORE presenting.
- When annotating in Figma: notes sit beside the frame, tied to finding numbers, per the
  canvas discipline in FIGMA-MAP.md.
- Record the critique outcome: Jira comment on the relevant ticket + CHANGELOG entry when
  changes result.
